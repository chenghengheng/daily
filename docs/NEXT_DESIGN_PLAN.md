# Daily 下一阶段功能设计计划

## 1. 目标

下一阶段把 Daily 从多个并列生活工具，进一步收束为一个低压力的个人选择助手：

> 随手记下 → 在合适的时间选一个 → 实际投入 → 留下一段经历 → 定期温和回顾。

本阶段不改变产品的本地优先定位，不引入完整任务管理、严格预算、社交、连续打卡或复杂日历。

## 2. 已确认的产品决策

1. “仪表盘”更名为“现在”。
2. “现在”页仍保留消费统计，但统计是次要信息，不抢占当前行动入口。
3. 保留现有底部导航结构，不进行导航合并或删减。
4. 推荐增加轻量反馈，并明确反馈的后续用途。
5. 重点建设“待选 → 进行中 → 经历过”的闭环。
6. 增加温和月度回顾。
7. 媒体元数据采用专门数据源；LLM 不作为影视片长数据库。

## 3. 阶段一：“现在”页重构

### 3.1 页面目标

“现在”页优先回答：

1. 现在有没有需要注意的事？
2. 我有一段空闲时间，可以做什么？
3. 我最近把时间和钱花在了哪里？

### 3.2 信息顺序

建议从上到下排列：

1. **到期提醒**
   - 只展示最近或已经到期的 1～3 条。
   - 没有提醒时不占空间。
2. **我现在有空**
   - 保留 10、20、45、60、120 分钟及自定义。
   - 如果已有进行中的计时，优先显示“继续”。
3. **推荐结果**
   - 一次只展示一个候选事项。
   - 显示类型、预计投入时长和推荐理由。
4. **本月非必要消费**
   - 显示本月总额。
   - 显示计划型与即时型的简单拆分。
   - 提供进入“随手花”的入口。
5. **等待进度摘要**
   - 显示进行中愿望数量、达到等待目标的数量和总等待进度。
   - 继续明确“不是余额或存款”。

消费统计保留在页面上，但视觉权重低于“我现在有空”和进行中的事项。

### 3.3 推荐理由

理由由确定性本地规则生成，不依赖 LLM。例如：

- “你有 20 分钟，这件事最短需要 15 分钟。”
- “这件事已经等待 36 天，最近没有推荐过。”
- “这部电影约 2 小时，适合现在一次看完。”
- “上次你认为 20 分钟不够，这次按 45 分钟推荐。”

理由必须能追溯到实际参与评分的因素，不能生成无法解释的泛化文案。

## 4. 推荐轻量反馈及其用途

### 4.1 推荐卡片上的反馈

保留三个主要动作：

- `开始`
- `换一个`
- `现在不适合`

完成一次投入后提供：

- `完成了`
- `做到一部分`
- `时长不准`

### 4.2 各反馈的后续用途

| 反馈 | 立即效果 | 长期效果 |
|---|---|---|
| 开始 | 创建投入记录并开始计时 | 增加该事项在相似可用时长下的“曾被接受”证据 |
| 换一个 | 本次推荐序列不再立即重复该事项 | 只产生极弱负向信号，不解释为“不喜欢” |
| 现在不适合 | 当天或当前时间段不再推荐 | 仅在相似时间段累计多次后形成弱偏好 |
| 完成了 | 结束本次投入；一次性事项退出推荐池 | 记录实际时长，改善以后同类事项的时长估计 |
| 做到一部分 | 候选事项进入或保持“进行中” | 下次可优先提供“继续”，但不垄断推荐 |
| 时长不准 | 询问“更短 / 约 1 小时 / 约 2 小时 / 需要一次完成” | 更新该事项自身时长；同类偏好至少累计 3 次后才调整 |

### 4.3 反馈使用原则

1. 单次“换一个”绝不形成长期不喜欢。
2. “现在不适合”首先解释为情境不合适，而不是事项质量差。
3. 事项自身校准优先于类型级偏好。
4. 类型级偏好必须由至少 3 次一致行为形成。
5. 弱偏好随时间衰减；建议 30 天内逐步减弱。
6. 用户归档或明确暂不推荐，权重高于推断出的弱偏好。
7. 设置中继续提供“清除推荐历史”和“恢复默认偏好”。

## 5. “待选 → 进行中 → 经历过”闭环

### 5.1 设计原则

候选事项和经历必须分开：

- 候选事项描述“未来还可以选择什么”。
- 经历描述“过去实际投入过什么”。

一次投入可以生成经历，但不一定完成候选事项。因此，“经历过”不是候选事项的终止状态。

### 5.2 事项类型对应的动作

| 类型 | 开始前 | 投入结束动作 | 完成后的表达 |
|---|---|---|---|
| 电影 | 待看 | 看完 / 没看完 | 看过 |
| 剧集 | 待看 | 看了一集 / 继续看 / 看完本剧 | 看过一段 / 已看完 |
| 书 | 待读 | 读了一会 / 读完 | 读过一段 / 已读完 |
| 事情 | 待做 | 做到一部分 / 做完 | 做过 / 已完成 |
| 想法 | 待处理 | 记录了一点 / 已处理 | 思考过 / 已处理 |

界面使用符合类型的语言，但底层仍共享“投入”和“完成”两个核心概念。

### 5.3 一次性与可重复

新增候选事项属性：

- `一次性`：完成后退出推荐池，如电影、一次性预约。
- `可重复`：每次投入都形成经历，但候选事项继续保留，如散步、练琴。
- `持续型`：可以多次投入，用户最终可以明确完成，如一本书、一部剧。

默认建议：

- 电影：一次性。
- 剧集、书：持续型。
- 普通事情：一次性。
- 想法：持续型。
- 用户可以在详情中调整。

### 5.4 投入记录

每次开始后立即创建一条投入草稿，至少包含：

- 关联候选事项；
- 开始时间；
- 计划投入分钟数；
- 来源：推荐开始或用户主动继续。

结束时补充：

- 实际投入分钟数；
- 结果：部分进行、完成、中止；
- 可选的一句话感受；
- 可选的时长校准。

异常处理：

- 刷新或关闭应用后可以恢复未结束投入。
- 原候选事项被归档时，既有经历继续保留。
- 删除候选事项前提示是否保留匿名化经历；默认保留经历标题快照。

### 5.5 “经历过”视图

第一版放在候选事项页面下方，以折叠区域呈现，不新增导航入口。

默认按时间倒序显示：

- 日期；
- 标题与类型；
- 实际投入时长；
- “看过 / 读过一段 / 做完”等结果；
- 可选感受。

支持的最小筛选：

- 全部；
- 完成；
- 部分进行。

第一版不增加评分、长评论、封面墙、社交分享或复杂统计。

### 5.6 关键验收场景

1. 看完电影后产生一条“看过”经历，电影退出推荐池。
2. 读书 20 分钟后产生一条“读过一段”经历，书进入“进行中”并可继续推荐。
3. 完成一次散步后产生经历，但“散步”仍留在推荐池。
4. 计时中刷新页面，可以继续或结束本次投入。
5. 归档事项不会删除已有经历。
6. 删除事项时不会静默删除经历。

## 6. 媒体元数据方案

### 6.1 目标

元数据只用于减少手动输入和提高时间推荐准确性：

- 标题；
- 年份；
- 类型；
- 电影片长；
- 剧集单集典型时长；
- 封面（可选）；
- 外部来源 ID。

不在 Daily 中建设影视评分、演员表、评论或播放平台聚合。

### 6.2 推荐数据源

#### 电影与剧集：TMDB

TMDB 提供电影/剧集搜索和详情数据，应用级访问需要 API Key 或 Read Access Token。由于 Daily 是静态 PWA，不应把共享 Token 直接写入前端代码。参考：[TMDB 应用认证](https://developer.themoviedb.org/v4/docs/authentication-application)。

建议调用链：

1. 用户选择“电影”或“剧集”并输入标题。
2. 用户停止输入约 400～600 毫秒后发起搜索。
3. 展示最多 3 个结果：标题、年份、封面缩略图。
4. 用户确认具体作品。
5. 获取详情并保存片长、来源 ID 和确认时间。
6. 无匹配时保留手动事项，不阻止保存。

#### 书籍：Open Library

Open Library 提供公开的低频实时搜索、作品、版本和封面数据，适合个人应用的按需查询；官方要求避免高频批量使用并建议缓存结果。参考：[Open Library API](https://openlibrary.org/developers/api)、[Search API](https://openlibrary.org/dev/docs/api/search)。

第一版书籍只保存标题、作者、首版年份、封面和 Open Library ID，不尝试根据页数推算阅读时长。

### 6.3 凭证与部署选择

推荐方案是一个无状态 Serverless 代理：

- 前端只发送标题、媒体类型和选中的来源 ID；
- 代理持有 TMDB Token；
- 不保存用户数据；
- 只允许固定上游地址和固定字段；
- 设置超时和基本频率限制；
- 上游失败时返回可理解错误；
- 不把候选列表、经历或消费历史发送给代理。

如果暂时不增加代理，媒体元数据应延后，而不是把共享 TMDB Token 写入前端。

### 6.4 本地缓存

用户确认作品后，把必要元数据写入候选事项。以后推荐和离线展示直接使用本地副本，不依赖每次联网。

建议记录：

- 来源名称；
- 来源 ID；
- 获取时间；
- 标题和年份；
- 片长或单集时长；
- 封面 URL（可选）；
- 用户是否手动覆盖时长。

用户手动覆盖的时长优先于外部数据，后续刷新元数据不得覆盖。

### 6.5 LLM 的角色

元数据接入后，优先级为：

1. 用户手动确认或修改；
2. 专门元数据；
3. 本地保守默认值；
4. LLM 对模糊事项进行补充。

LLM 不再负责猜测已确认电影的片长。

## 7. 温和月度回顾

### 7.1 入口与触发

- 在“现在”页消费摘要下提供“查看本月回顾”。
- 每月第一周可以出现一次非阻塞提示。
- 用户可以关闭提示；不使用红点催促。

### 7.2 回顾内容

#### 选择与投入

- 本月完成了多少个一次性事项；
- 对多少个持续型事项有过投入；
- 总投入时长；
- 最常继续的事项；
- 预计与实际时长差异最大的事项。

#### 愿望

- 新增多少个愿望；
- 经过等待后购买多少个；
- 提前购买多少个；
- 放弃或归档多少个；
- 当前仍在等待多少个。

#### 非必要消费

- 本月实际总额；
- 计划型与即时型拆分；
- 分类分布；
- 与上月相比的中性变化。

#### 推荐反馈

- 推荐被接受次数；
- 换一个次数；
- “现在不适合”次数；
- 发生过时长校准的事项。

### 7.3 文案原则

使用：

- “本月即时型消费比上月多 ¥80。”
- “有 3 次推荐最终开始执行。”
- “阅读通常比最初预计多投入约 15 分钟。”

避免：

- “超支”
- “失败”
- “控制不住”
- “连续打卡中断”
- “完成率过低”

### 7.4 空数据与小样本

- 数据不足时只展示事实，不生成趋势结论。
- 少于 3 次行为时不推断偏好。
- 没有上月数据时不显示环比。
- 月度回顾完全由本地数据生成，不调用 LLM。

## 8. 分阶段实施顺序

### 阶段 A：现在页与可解释反馈

1. 仪表盘更名为“现在”。
2. 调整信息顺序，并保留消费统计。
3. 推荐卡片增加本地理由。
4. 完善轻量反馈事件与衰减规则。

验收重点：不增加录入步骤；推荐理由可由本地数据解释。

### 阶段 B：投入与经历闭环

1. 建立投入记录。
2. 区分一次性、持续型和可重复事项。
3. 增加类型化结束动作。
4. 增加“经历过”折叠视图。
5. 计时恢复与投入草稿统一。

验收重点：部分进行、完成、重复活动和刷新恢复均不会丢失历史。

### 阶段 C：温和月度回顾

1. 生成本地月度汇总。
2. 增加回顾页面或 Modal。
3. 增加中性环比与小样本保护。

验收重点：不出现预算压力文案，不依赖 LLM。

### 阶段 D：媒体元数据

1. 先确认 Serverless 代理部署方式。
2. 接入电影/剧集搜索与确认。
3. 接入书籍搜索。
4. 缓存已确认元数据并支持手动覆盖。
5. 降低 LLM 在媒体时长上的职责。

验收重点：网络和数据源失败不阻止保存，Token 不进入前端或备份。

## 9. 明确不在下一阶段实施

- 修改或精简底部导航；
- 完整日历和自动时间块排程；
- 严格预算、收入、账户和余额；
- 影视评分、评论和社交；
- 复杂标签、筛选器和智能列表；
- 连续打卡、积分、等级和成就；
- 由 LLM 直接修改推荐记忆或事项状态；
- 云端数据库和多设备同步。

## 10. 成功指标

第一版不做遥测，使用本地可见指标进行产品判断：

- 从选择可用时间到开始事项的操作不超过 2 次点击；
- 部分进行后可以在“现在”页一键继续；
- 每条经历都能追溯到一次真实投入；
- 用户可以解释为什么某事项被推荐；
- 月度回顾只陈述事实和弱趋势；
- 外部元数据失败时，所有核心流程仍然可用。
